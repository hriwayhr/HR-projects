# HR-метрики в Yandex Cloud

Та же страница, что на claude.ai, но на своём адресе в Yandex Cloud: вход — корпоративным
аккаунтом Яндекс 360, данные — в базе YDB в России, права проверяет сервер.

## Как устроено

```
браузер ──HTTPS──▶ API Gateway ──▶ Cloud Function (hr-api) ──▶ YDB (hr-db)
                                        │  └─ вход: Яндекс ID (OAuth), только почты вашего домена из «Команды»
                                        └─ каждую ночь — копия базы ──▶ Object Storage (hr-backups-…)
```

- **Вход** — через Яндекс ID. Пускаем только почты домена компании (`DOMAIN`), которые администратор
  внёс в «Команду» и не отправил в архив. Своих паролей больше нет: двухфакторная защита, блокировка
  уволенного и смена пароля — в Яндекс 360. Сессия — 8 часов в cookie `HttpOnly; Secure; SameSite=Lax`,
  подписанной ключом из Lockbox. Членство в команде проверяется на **каждом** запросе: убрали почту или
  отправили в архив — доступ закрыт сразу. При первом входе почта привязывается к аккаунту Яндекса:
  войти тем же адресом с другого аккаунта (например, личного Яндекс ID, к которому привязан рабочий
  адрес) нельзя. Исправили человеку почту в «Команде» — привязка сбрасывается.
- **Права — на сервере** (`function/acl.js`). Рекрутер получает с сервера только свои цифры, свой
  отпуск, свои вакансии и свои отказы; почты коллег не видит; записать может только своё. Настройки,
  команда, метрики, Talantix и удаление вакансий — только администратор. Подделать запрос в обход
  страницы не выйдет: сервер не знает «страницу», он проверяет пользователя.
- **База** — YDB serverless; из интернета к ней не подключиться, доступ — только у функции
  (сервисный аккаунт `hr-fn`, роль `ydb.editor` на эту базу). Каждая запись — в транзакции, плюс строка
  в таблице `audit`: кто, что и когда менял.
- **Секреты** (ключ подписи сессий, секрет OAuth-приложения) — в Lockbox, в функцию попадают
  переменными окружения; в коде и на странице их нет.
- **Страница** отдаётся со строгими заголовками: CSP (только свои скрипты, с одноразовым nonce;
  никаких внешних CDN), запрет встраивания во фреймы, HSTS, `Referrer-Policy: no-referrer`.
  Запись принимается только с заголовком `X-HR` — так чужой сайт не отправит запрос от имени
  вошедшего пользователя.
- **Ночная копия** всей базы — JSON в закрытый бакет с включёнными версиями (каждый день в 02:00 МСК).

## Что нужно до начала

1. Аккаунт в Yandex Cloud с платёжным аккаунтом. Почти всё укладывается в бесплатные лимиты
   (функции, шлюз, YDB serverless, 1 ГБ хранилища) — проверьте текущие лимиты на странице тарифов.
2. **Отдельный каталог** в облаке только для этого приложения (например, `hr-metrics`): права сервисных
   аккаунтов выдаются на каталог, и в нём не должно быть ничего постороннего.
3. На компьютере, откуда разворачиваете: [yc](https://yandex.cloud/ru/docs/cli/quickstart) (после
   `yc init`), `jq`, `python3`, `openssl`.
4. Двухфакторная аутентификация на аккаунте, которым входите в консоль облака.

## Развёртывание

```bash
cd cloud
# 1-й запуск: база, бакет, функция, шлюз. В конце — адрес для регистрации приложения в Яндекс ID.
FOLDER_ID=b1g…  DOMAIN=iway.ru  ADMIN_EMAIL=you@iway.ru  ./deploy.sh
```

Зарегистрируйте приложение на <https://oauth.yandex.ru/client/new> (под корпоративным аккаунтом):
платформа «Веб-сервисы», Redirect URI — из вывода скрипта (`https://…apigw.yandexcloud.net/api/callback`),
доступ «Доступ к адресу электронной почты». Скопируйте ClientID и Client secret.

```bash
# 2-й запуск: секреты → Lockbox, сборка и выкладка функции, ночные копии
FOLDER_ID=b1g…  DOMAIN=iway.ru  ADMIN_EMAIL=you@iway.ru \
OAUTH_CLIENT_ID=…  OAUTH_CLIENT_SECRET=…  ./deploy.sh
```

Откройте адрес из вывода и войдите почтой из `ADMIN_EMAIL` — вы станете первым администратором.
Почта из `ADMIN_EMAIL` становится администратором сама, только пока в команде нет ни одного
администратора с почтой, — дальше администраторов назначают в «Команде».

## Перенос данных с claude.ai

1. В версии на claude.ai: **Настройки → Резервная копия → Скачать резервную копию**. Паролей в файле нет.
2. В облачной версии: **Настройки → Резервная копия → Загрузить копию**, выберите файл, укажите,
   кто вы в загруженной команде, — нажмите «Загрузить».
3. **Настройки → Команда**: впишите каждому корпоративную почту. Без почты человек войти не сможет.
   Тестовую учётную запись (test) отправьте в архив.
4. Удалите скачанный файл копии с компьютера — в нём персональные данные.

## Обновление

После изменений в `src/hr-metrics.html` или `cloud/function/` — тот же 2-й запуск `deploy.sh`:
он соберёт и выложит новую версию функции. Секреты и база не меняются.

## Проверка безопасности — раз в квартал

- Кто имеет доступ к каталогу в консоли облака (IAM → Права доступа) — только те, кому нужно.
- В «Команде» нет уволенных (архив) и чужих почт.
- В бакете `hr-backups-…` появляются ночные копии; бакет закрыт (нет публичного доступа).
- Журнал функции (Cloud Logging) без потока ошибок 401/403 с одного адреса.

## Чего здесь нет (сознательно)

- Своего домена (например, `hr.iway.ru`): работает адрес `…apigw.yandexcloud.net`. Свой домен
  подключается в API Gateway с сертификатом из Certificate Manager.
- Ограничения частоты запросов на шлюзе: перебор паролей невозможен (входа по паролю нет).
- Удаления старых копий: включите правило жизненного цикла бакета (например, 180 дней) в консоли.
- Юридической части 152-ФЗ: уведомление Роскомнадзора, политика обработки, согласия кандидатов —
  на стороне компании как оператора данных.
